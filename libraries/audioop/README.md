# audioop (Mojo Port)

## Status: PHASE 10 COMPLETE — all 26 operations implemented and benchmarked (pre-release)

## Library description

Legacy operations on raw audio samples: sample-width conversion, channel
conversion, gain, bias, clipping, RMS, peak, and related transforms. The module
was part of the Python standard library and was removed in Python 3.13 under
PEP 594, so a native implementation is useful for code maintaining that
behaviour.

## Original Python package

- Reference: CPython **3.12.3** `audioop` (C extension). The module was
  deprecated in 3.11 and removed in 3.13, so the reference is used through an
  isolated 3.12 interpreter in `python_reference/.venv`.
- Provenance, hashes, build-equivalence proof, and license chain:
  [`docs/reference-audit.md`](docs/reference-audit.md) and
  [`docs/licensing-audit.md`](docs/licensing-audit.md).
- Upstream source is not vendored; the port is independent and no code was
  copied.

## Planned Mojo implementation

Native sample-buffer transforms over 8-, 16-, 24-, and 32-bit integer
samples. Phase 0 froze the v0.1 scope to all 26 reference functions, native
byte order (no endianness parameter exists upstream), bytes fragments, and
reference-compatible sentinels and error messages. See
[`docs/api-scope.md`](docs/api-scope.md) and
[`PHASE0_RESULTS.md`](PHASE0_RESULTS.md).

Phase 1 implements the internal signed-sample layer used by every
operation: width/fragment validation, single-sample and fragment
decode/encode, native byte order, and 24-bit sign extension. See
[`docs/sample-representation.md`](docs/sample-representation.md) and
[`PHASE1_RESULTS.md`](PHASE1_RESULTS.md).

Phase 2 implements the first six public operations on that layer:
`add` (saturating), `bias` (wrapping), `mul` (clamp-then-floor), `reverse`,
`byteswap`, and `lin2lin`. See
[`docs/arithmetic-operations.md`](docs/arithmetic-operations.md) and
[`PHASE2_RESULTS.md`](PHASE2_RESULTS.md).

Phase 3 implements six statistics operations: `getsample`, `max`
(absolute magnitude), `minmax`, `avg` (floor), `rms`, and `cross`. See
[`docs/statistics-operations.md`](docs/statistics-operations.md) and
[`PHASE3_RESULTS.md`](PHASE3_RESULTS.md).

Phase 4 implements five peak-analysis/matching operations: `avgpp`,
`maxpp`, `findmax`, `findfactor`, and `findfit`. See
[`docs/peak-analysis.md`](docs/peak-analysis.md) and
[`PHASE4_RESULTS.md`](PHASE4_RESULTS.md).

Phase 5 implements the channel operations `tomono` and `tostereo`. See
[`docs/channel-operations.md`](docs/channel-operations.md) and
[`PHASE5_RESULTS.md`](PHASE5_RESULTS.md).

Phase 6 implements the stateful sample-rate converter `ratecv`. See
[`docs/ratecv.md`](docs/ratecv.md) and
[`PHASE6_RESULTS.md`](PHASE6_RESULTS.md).

Phase 7 implements the G.711 codecs `lin2alaw`, `alaw2lin`, `lin2ulaw`,
and `ulaw2lin`. See [`docs/g711.md`](docs/g711.md) and
[`PHASE7_RESULTS.md`](PHASE7_RESULTS.md).

Phase 8 implements the Intel/DVI ADPCM codec `lin2adpcm`/`adpcm2lin`,
completing the 26-operation v0.1.0 API. See
[`docs/adpcm.md`](docs/adpcm.md) and
[`PHASE8_RESULTS.md`](PHASE8_RESULTS.md).

## Compatibility objectives

- Match reference results for supported sample widths and operations.
- Preserve saturating and wrapping behaviour exactly where the reference
  distinguishes them.
- Handle empty buffers, odd buffer lengths, and fragment counts as the
  reference does.
- Document any operation intentionally excluded from the port.

## Testing requirements

- Mojo unit tests for each supported operation and sample width.
- Python compatibility tests against the reference implementation.
- Golden vectors including boundary amplitudes, silence, and malformed buffer
  lengths. The corpus now has 1277 cases: the original 42 function cases,
  24 sample-representation cases, 50 Phase 2 arithmetic cases, 69 Phase 3
  statistics cases, 58 Phase 4 peak-analysis cases, 33 Phase 5 channel
  cases, 31 Phase 6 ratecv cases, 645 Phase 7 G.711 cases (all 256 A-law
  and mu-law decoder codewords), and 325 Phase 8 ADPCM cases (all 256
  decoder byte values), generated by the pinned reference and guarded by
  `--check` drift detection.

## Benchmark results (Phase 10)

- Three-way comparison (naive Python, reference C, native Mojo) plus a
  separately measured CLI request path, over 250 deterministic workloads.
  See [`benchmarks/`](benchmarks/) and
  [`benchmarks/reports/BENCHMARK_REPORT.md`](benchmarks/reports/BENCHMARK_REPORT.md).
- Headline (median-of-medians): native Mojo is ~15–110× faster than the
  pure-Python floor and typically ~0.05–0.5× of CPython C speed (C is
  ~2–20× faster); `getsample` is ~2–3× Mojo-faster as both are O(1).
- CLI response time is dominated by process spawn (~16 ms floor); it is
  not a measure of kernel performance.
